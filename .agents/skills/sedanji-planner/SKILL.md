# Sedanji Planner

## 적용과 권한

- Thread B의 코드 분석·설계·계획·독립 리뷰에 적용한다. 일반 설명이나 승인된 구현을 이유 없이 계획 단계로 되돌리지 않는다.
- 기본은 읽기 전용이다. 파일 생성·수정, Git 상태 변경(stage·stash·reset·브랜치 변경·커밋·Push 등), 테스트·빌드, 설치, Docker·실제 DB·실제 외부 API 작업을 하지 않는다. Handoff도 대화에 작성하며 자동 저장하지 않는다.
- 사용자에게 명시적으로 별도 권한을 받은 경우에만 해당 작업을 수행한다. 계획 승인과 실행 권한을 구분하고, 코드 구현으로 전환하면 [Implementer](../sedanji-implementer/SKILL.md)를 읽어 단계·범위를 갱신한다. 이미 충분히 승인된 사항은 반복 승인받지 않는다.
- [루트 지침](../../../AGENTS.md)을 읽고 관련 영역의 [Backend](../../../backend/AGENTS.md)·[Frontend](../../../frontend/AGENTS.md) 지침을 확인한다. 실제 구현·테스트를 사실 근거로 삼고 설계 문서의 계획·과거 기록은 구분한다.
- 검증 계획·테스트 선택·검증 보고에는 [Verification](../sedanji-verification/SKILL.md), API 계약 영향에는 [API Change](../sedanji-api-change/SKILL.md), 저장 모델·스키마·Flyway 영향에는 [DB Migration](../sedanji-db-migration/SKILL.md)을 추가 적용한다. 전문 Skill의 절차는 실행 권한을 확대하지 않으며 분석만 하면 테스트를 실행하지 않는다.
- 시작 시 실제 읽은 역할·전문 SKILL.md 경로, 이번 적용 규칙, 미적용 전문 Skill과 이유, 실행 권한·제한을 간단히 보고한다. 이름만 언급하거나 파일이 있다는 이유로 적용했다고 하지 않는다. 파일이 없거나 읽을 수 없으면 적용 완료로 보고하지 않는다. 자동 선택은 보장하지 않는다.

## 분석·설계

1. 저장소 루트·현재 브랜치·HEAD와 staged/unstaged/untracked를 확인한다. Git 조회 실패를 변경 없음으로 처리하지 않는다. 기존 사용자 변경과 분석 대상을 구분하고 비밀값은 출력하지 않는다.
2. 목표·완료 조건·제외 범위를 분해하고 실제 코드·설정·테스트·관련 문서를 연결한다. 현재 구현, 확정 요구, 제안, 미정을 분리한다. 현재 작업에 필요 없는 기능·기술 전환을 추가하지 않는다.
3. 기존 호출 흐름에서 클래스·메서드 책임과 변경 위치를 설계한다. API·DTO·Frontend 소비자, JPA·Repository·기존 데이터·배포 영향을 확인하며 영향 없음도 근거를 적는다. 의미 있는 대안과 권장 이유를 제시한다.
4. 승인 트랜잭션·잠금·롤백·중복 방지, 세션·권한·CSRF, 후보 매칭과 관계 승인의 구분, `APPROVED AND PUBLISHED`, 내부 정보 비공개 및 null/0 처리를 관련 범위에서 검토한다. 상세 규칙은 기존 영역 지침·전문 Skill을 따른다.
5. 요구사항마다 `fixture/사전 조건 → 호출·행위 → 기대 상태·응답·저장 결과 assertion`을 정의한다. 성공뿐 아니라 관련 거부·롤백·중복·동시성 사례를 포함하고 기존 테스트의 실제 assertion과 공백을 확인한다. 테스트 이름·통과 이력만으로 충족을 선언하지 않는다.
6. 필요한 사용자 결정·승인·검증 권한을 분리한다. 미승인 비즈니스 결정을 임의 확정하지 않는다. 독립적으로 분석 가능한 부분은 계속 진행한다.

## Implementation Handoff 표준

이전 스레드 대화 없이 구현자가 이해하도록 아래 항목을 대화에 작성한다. 해당 없음은 근거와 함께 명시하고, 중요한 정보를 외부 대화 링크만으로 대체하지 않는다.

| 항목 | 전달 내용 |
| --- | --- |
| 식별·상태 | 기능명·Handoff 버전, 기본 `PROPOSED` 및 작성 시점 |
| 저장소 기준 | 저장소 루트, 분석 브랜치·전체 커밋 SHA, 관련 staged/unstaged/untracked 내용과 기존 변경 경계 |
| 목표·완료 조건 | 요구 동작과 관측 가능한 성공 조건 |
| 범위·제외 | 구현 영역·예정 파일, 이번에 만들지 않을 기능 |
| 현재 구현 근거 | 코드·테스트·설정·문서 경로와 중요한 구현/설계 차이 |
| 결정·승인 | 결정별 PROPOSED/APPROVED/미정, 사용자 명시 승인 근거와 범위·제한 |
| 설계 | 클래스·메서드별 책임, 호출·트랜잭션 흐름, 대안과 선택 이유 |
| API·DB·Frontend | 계약·호환성·소비자, 매핑·제약·migration·기존 데이터 및 배포 영향 |
| 불변식 | 보존할 승인·보안·공개·중복·데이터 무결성 규칙 |
| 테스트 | 요구사항별 fixture·실행 경로·구체적 assertion·기존 검증 공백 |
| 검증·실행 권한 | Verification 선택 영역·명령·환경·부작용, 실행 허용/금지, Git 작업 권한 |
| 보류·질문 | 필수 미정 결정, 저장소 기준 변경 시 재검토 조건, 필요한 추가 승인 |

- Planner가 작성한 Handoff는 기본 `PROPOSED`다. 사용자에게 명시적으로 승인받은 요구사항·범위만 `APPROVED`로 기록한다. 일부 승인으로 나머지 결정을 승인 처리하지 않는다.
- 문서의 `APPROVED` 표기는 구현 권한의 증명이 아니다. Thread C가 받은 사용자 지시와 승인 범위를 대조할 수 있도록 필요한 내용을 전달한다. 승인 근거가 없으면 승인됨으로 추정하지 않는다.
- 새 스레드가 이전 대화·환경·검증 결과를 자동 상속한다고 가정하지 않는다. 과거 PASS와 이번 미실행을 구분하고, 실제 DB를 조회하지 않았다면 적용 버전·정합성을 미확인으로 남긴다.

## 독립 리뷰 모드

- 리뷰 기준 Handoff·승인 범위·base/head 또는 작업 트리 diff를 먼저 확정한다. 구현자의 설명과 실제 변경을 대조하고 관련 테스트 assertion을 읽는다. 같은 스레드의 자기 점검을 별도 스레드의 독립 리뷰라고 표현하지 않는다.
- 기능 결함·보안/데이터 불변식 위반·호환성·범위 이탈·테스트 공백을 우선한다. 발견 사항에 파일·위치·발생 조건·영향·수정 방향을 적고 중요도순으로 보고한다. 근거가 없는 결함을 만들지 않는다.
- 승인된 계획 자체가 불변식과 충돌하면 그대로 승인하지 않고 보고한다. 리뷰를 이유로 코드를 고치거나 테스트를 실행하지 않는다. 별도 허용된 실행만 수행하며 Verification의 결과 보고를 따른다.
- 결과는 발견 사항, 미확인 사항·검증 공백, 승인 범위 충족 여부로 보고한다. 발견 없음은 무결함·운영 안전·미실행 테스트 통과를 의미하지 않는다.
