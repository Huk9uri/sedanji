# Sedanji Implementer

## 적용·승인 확인

- Thread C에서 승인된 Implementation Handoff를 구현할 때 적용한다. 설계·독립 리뷰만 요청되면 [Planner](../sedanji-planner/SKILL.md)를 사용한다. 승인된 구현 범위 안의 통상적인 코드·테스트 작성과 안전한 로컬 검증을 금지하지 않는다.
- [루트 지침](../../../AGENTS.md), 관련 영역의 [Backend](../../../backend/AGENTS.md)·[Frontend](../../../frontend/AGENTS.md) 지침을 읽는다. Handoff의 목표·완료 조건·결정별 승인 상태·제외 범위·실행 권한을 전달받은 사용자 지시와 대조한다.
- Handoff 기본 상태는 `PROPOSED`다. 사용자가 명시 승인한 요구사항·범위만 `APPROVED`로 취급한다. 문서 내부 APPROVED 표기, Planner의 권장안, Skill을 읽거나 적용한 사실은 수정·테스트·Git 작업의 권한이 아니다. 이전 스레드 승인이 자동 전달됐다고 가정하지 않는다.
- 분석에서 구현으로 전환할 때 필요한 권한을 확인한다. 승인된 Handoff와 구현 권한이 충분하면 반복 승인 없이 진행한다. 필수 비즈니스 결정이 미정이면 임의로 확정하지 않으며, 승인 범위 내 통상적 구현 선택까지 모두 다시 승인받지는 않는다.
- 시작 시 실제 읽은 역할·전문 SKILL.md 경로, 이번 적용 규칙, 미적용 전문 Skill과 이유, 실행 권한·제한을 짧게 보고한다. 파일이 없거나 읽을 수 없으면 적용 완료라고 하지 않고 제한을 알린다. 이름 언급·자동 선택만으로 실제 적용을 보장하지 않는다.

## 실제 저장소와 Handoff 대조

1. 저장소 루트·브랜치·현재 HEAD 및 staged/unstaged/untracked를 확인한다. Handoff의 기준 브랜치·커밋·관련 미커밋 변경과 대조하고 기존 사용자 작업을 식별한다.
2. 기준 커밋이 다르면 관련 diff·코드·계약·설정·테스트의 설계 영향을 분석한다. 관련 없는 변경만 있으면 차이와 근거를 보고하고 진행한다. 브랜치 이름이나 SHA 차이 자체를 중단 사유로 삼지 않는다. 기준 객체가 없으면 fetch·브랜치 변경 권한을 추정하지 말고 현재 파일로 확인 가능한 범위와 한계를 보고한다.
3. 설계에 영향을 주는 차이, 필수 결정 누락, 승인 범위 밖 DB/API 변경 필요, 보안·승인·공개 불변식 충돌이면 **해당 구현을 보류하고** 원인·영향·필요 결정·제안 범위를 보고한다. 독립적으로 승인된 작업만 계속할 수 있다. 기존 변경을 덮어쓰거나 stash/reset·삭제·재작성으로 없애지 않는다.

## 전문 Skill과 구현

- 검증 선택·실행·보고에는 [Verification](../sedanji-verification/SKILL.md)을 적용한다. API 계약 영향에는 [API Change](../sedanji-api-change/SKILL.md), DB·JPA 저장 모델·Flyway 영향에는 [DB Migration](../sedanji-db-migration/SKILL.md)을 추가한다. 전문 Skill은 사용자 권한을 확대하지 않으며 역할 Skill을 대체하지 않는다.
- 실제 실행 코드·설정·테스트를 근거로 기존 구조에 맞춰 최소 구현한다. 설계 문서를 이미 동작하는 계약으로 간주하지 않는다. 메서드 책임·트랜잭션 경계·잠금·동시성·중복 방지, 인증·CSRF, 후보 매칭/관계 승인 구분, `APPROVED AND PUBLISHED`와 내부 정보 비공개를 보존한다.
- API 변경은 Backend DTO·상태·오류·null과 Frontend 타입·래퍼·호출부를 함께 확인한다. 수정이 불필요한 영역도 근거를 보고한다. DB 변경은 승인된 후속 migration 원칙을 따르고 기존 migration을 임의 수정하지 않는다. 스키마 변경이 필요 없으면 migration을 만들지 않는다.
- 승인 범위에서 코드와 의미 있는 테스트를 작성한다. `요구사항 → 실제 실행 경로 → assertion`을 연결하고, 누락된 계약·롤백·중복·공개 조건 검증을 기존 전체 PASS로 대신하지 않는다. 필요한 추가 테스트가 범위 밖이면 공백을 보고한다.
- 검증은 현재 작업 트리에서 수행한다. 명령·종료 코드·각 검사 PASS/FAIL/NOT RUN·미실행 사유와 테스트 공백을 Verification 규칙대로 보고한다. 환경 부재면 임의 설치·Docker 시작·검증 설정 우회로 성공시키지 않는다. 실패 원인을 다룬 뒤 필요한 검증만 재판단한다.

## 실행 경계

- 구현 승인에 포함된 코드·테스트 작성과 실행 제한에 저촉되지 않는 안전한 로컬 검증은 수행한다. 별도 사용자 실행 금지가 있으면 실행하지 않는다. Testcontainers 임시 테스트 DB·그 DB의 Flyway, 빌드/보고서/캐시 산출물은 기존 검증의 허용 부작용이며 실제 개발·운영 DB와 구분한다.
- 실제 개발·운영 DB 접속·변경, 실제 외부 API 호출·비밀값 사용, 데이터 삭제·백필 실행을 하지 않는다. 비밀정보를 로그·응답·문서에 출력하지 않는다. 새 migration 작성 승인은 실제 DB 적용 승인이 아니다.
- 의존성·도구·이미지 자동 설치, Docker/서버 자동 시작을 하지 않는다. 모의 외부 API와 기존 임시 테스트 환경을 유지하고 존재하지 않는 Expo 앱을 가정하지 않는다.
- branch/stage/stash/reset·commit·Push·PR 생성·배포는 구현 승인만으로 수행하지 않는다. 각각 명시적으로 허용된 범위만 수행한다. 커밋안·PR 설명 초안 작성과 실제 외부 PR 생성은 구분한다.

## 완료·전달

- 승인 요구별 구현 상태, 변경 파일과 주요 메서드의 책임, Handoff 대비 차이·관련 없는 기준 변경·보류 항목을 보고한다. 부분 구현이나 검증 미완료를 전체 완료로 선언하지 않는다.
- 계약·DB/Frontend 영향, 보존한 불변식, 실제 검증 결과와 미실행·실패·남은 assertion 공백을 보고한다. `git diff --check` 및 신규 파일 공백·참조·범위를 확인하고 기존 사용자 변경 보존 여부를 확인한다.
- 권장 커밋 분리안과 문제·최종 동작·검증·한계를 담은 PR 설명을 대화에 작성한다. 사용자 요청 없이 별도 파일을 생성하지 않는다. 독립 리뷰가 필요하면 base/head·작업 트리 범위, 승인 Handoff와 실제 검증 증거를 Planner에 전달할 수 있도록 정리하며 스레드 생성·전송을 자동 수행하지 않는다.
