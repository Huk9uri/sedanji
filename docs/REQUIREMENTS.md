# 세단지 요구사항 명세서

버전: 0.1 · 작성일: 2026-11-01 · 상태: 사용자 검토용 초안

## 1. 문서 목적과 합의 기준

사용자용 모바일 앱과 관리자용 웹의 제품 요구사항을 정리한다. 기존 웹 프로토타입의 화면 구성이나 구현 기술을 제품의 확정 설계로 취급하지 않는다.

| 구분 | 의미 |
| --- | --- |
| 확정 | 대화에서 사용자가 명시적으로 정했거나 동의한 사항 |
| 지침 | AGENTS.md의 기존 도메인·데이터 신뢰성·보안 원칙 |
| 제안 | 검토를 위한 권고안이며 구현 승인으로 간주하지 않음 |
| 미정 | 별도 논의가 필요한 사항 |

이 문서 전체가 최종 승인된 것은 아니다. 요구사항의 기재 순서는 개발 순서나 첫 출시 범위를 확정하지 않는다. 확정 사항을 바꾸거나 미정 사항을 구현하려면 먼저 사용자와 협의한다.

## 2. 서비스 목적

셰프가 방문하거나 추천하거나 단골로 언급한 식당을 발견하고, 어떤 셰프가 어느 영상에서 어떤 맥락으로 소개했는지 출처를 확인할 수 있는 서비스다.

자동 추출만으로 모든 식당과 관계를 확보할 수 있다고 가정하지 않는다. 관리자 직접 등록, 사용자 제보, 자동 추출 보조를 통해 후보를 확보하되 검증과 공개를 구분한다.

## 3. 서비스 구성과 이용자

| ID | 구분 | 요구사항 |

| SVC-03 | 확정 | 일반 사용자용 탐색 웹을 제품 범위에 포함하지 않는다. 현재 React 웹의 사용자 지도는 프로토타입 이력으로 취급한다 |
| SVC-04 | 지침 | 모바일 앱과 관리자 웹은 공통 백엔드와 검증된 식당·관계 데이터를 사용한다 |

| 역할 | 이용 범위 |
| --- | --- |
| 비로그인 사용자 | 공개된 식당과 셰프·영상 관계 탐색 |
| 로그인 사용자 | 공개 탐색과 본인 저장 목록 이용 |

관리자 로그인과 일반 사용자 로그인은 권한을 분리한다. 일반 사용자 로그인이 관리자 권한을 부여하지 않는다.

### 일반 사용자 로그인 방식 — 확정

| ID | 구분 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| AUTH-01 | 확정 | 일반 사용자는 소셜 로그인만 이용한다 | 별도 이메일·비밀번호 회원가입 및 로그인을 제공하지 않는다 |
| AUTH-02 | 확정 | iOS·Android 공통으로 카카오·구글·네이버 로그인을 제공한다 | 두 플랫폼 모두 카카오·구글·네이버 계정으로 로그인할 수 있다 |
| AUTH-03 | 확정 | iOS에만 Apple 로그인을 추가한다 | iOS는 카카오·구글·네이버·Apple, Android는 카카오·구글·네이버 로그인을 제공한다 |
| AUTH-04 | 확정 | 일반 사용자는 명시적으로 로그아웃하기 전까지 로그인 상태를 유지한다 | 앱 종료·재실행 후에도 로그인을 유지한다. 30일 미사용 또는 로그인 후 90일 경과 같은 시간 조건으로 재로그인을 요구하지 않는다 |
| AUTH-05 | 확정 | 서로 다른 소셜 제공자로 로그인하면 별도 세단지 계정으로 취급한다 | 같은 사람이 카카오와 구글 등 서로 다른 제공자로 로그인해도 저장 목록과 제보 내역을 공유하지 않는다. 이메일이 같아도 자동 병합하지 않으며 첫 출시에는 계정 연결·병합 기능을 제공하지 않는다 |

동일 제공자의 동일 사용자로 다시 로그인하면 기존 세단지 계정에 연결한다. 계정 식별은 제공자와 해당 제공자의 사용자 식별자를 기준으로 하며 이메일만으로 동일 계정을 판단하지 않는다.

회원 탈퇴 또는 인증 정보의 폐기·무효화로 인증을 계속할 수 없는 경우에는 로그인 상태를 종료한다. 이 정책은 일반 사용자의 로그인 유지에 관한 것이며 관리자 인증에는 자동 적용하지 않는다. 개별 토큰을 영구 유효하게 만든다는 의미가 아니며, 토큰 수명·자동 갱신·안전한 보관 방식은 별도 기술 설계에서 정한다. 앞서 제안한 액세스 토큰 30분·리프레시 토큰 30일·최대 로그인 90일은 확정하지 않는다.

iOS의 로그인 정책에 대응하기 위해 Apple 로그인을 iOS 전용으로 제공한다. Android에는 Apple 로그인을 제공하지 않는다. 실제 구현과 심사 제출 시에는 각 제공자의 연동 요건과 최신 정책을 확인한다.

이 결정은 일반 사용자 인증에 관한 것이며 기존 관리자 인증 방식의 변경을 의미하지 않는다. 정책 확인 근거: [Apple 심사 지침 4.8](https://developer.apple.com/app-store/review/guidelines/#login-services), 2026-11-01 확인.

### 첫 출시 범위 — 확정

첫 출시에는 지도 탐색, 식당 상세, 개인 저장, 맛집 제보를 모두 포함한다. 셰프 필터도 첫 출시부터 제공한다. 비로그인 탐색, 저장·최종 제보 제출 시 로그인, 관리자 검증 후 공개 원칙을 적용한다. 각 기능의 세부 미정 사항이 모두 승인된 것은 아니며 출시 일정은 별도로 합의한다.

### 개발 순서 — 확정

1. 관리자 식당 등록·관계 승인
2. 모바일 지도 탐색·상세·영상·셰프 필터
3. 소셜 로그인·개인 저장
4. 사용자 제보·관리자 제보 처리
5. 내 제보 상태 조회 — 후순위

검증된 식당과 관계를 관리자 도구로 확보한 뒤 모바일 탐색과 사용자 기능을 순서대로 구현한다. 이 순서는 첫 출시 범위를 줄이는 결정이 아니다. 내 제보 상태 조회의 첫 출시 전 완료 또는 출시 후 제공 여부는 기존 합의대로 미정이며, 후순위 구현으로 유지한다. 각 단계의 상세 설계와 미정 요구사항은 구현 전에 검토한다.

### 사용자 앱 구현 기술 — 확정

사용자용 iOS·Android 앱은 React Native + TypeScript로 개발하고, Expo Development Build를 사용한다. React 기반 개발 방식을 활용하면서 두 플랫폼의 공통 기능을 함께 개발하기 위한 선택이다. 기존 관리자 웹과 공통 백엔드의 기술 변경을 의미하지 않는다.

앱 화면은 모바일용으로 별도 설계하며 기존 React 웹 화면을 그대로 재사용한다고 가정하지 않는다. 네이티브 SDK 연동은 Development Build에서 검증하고 Expo Go만으로 동작을 보장하지 않는다.

### 모바일 지도 연동 방식 — 확정

사용자 앱의 지도는 카카오 Android·iOS 네이티브 지도 SDK를 React Native에 연결하여 구현한다. WebView에 JavaScript 지도를 넣는 방식은 사용자 앱의 지도 구현 방식으로 채택하지 않는다. 관리자 웹의 지도 기술 변경을 의미하지 않는다.

연결 라이브러리 사용 또는 직접 연결 코드 작성 여부와 상세 버전은 구현 검토 사항이다. 필요한 마커 표시·선택·지도 이동 기능과 Expo Development Build 및 양 플랫폼의 호환성을 확인한 뒤 구체적인 방안을 제안한다. 이번 결정은 라이브러리 선정이나 실제 연동 검증 완료를 의미하지 않는다.

## 4. 사용자 앱 요구사항

### 하단 내비게이션 — 확정

사용자 앱의 주요 메뉴 이동에는 아이콘과 메뉴명을 함께 표시하는 하단 내비게이션 바를 제공한다. 사용자가 현재 어느 메뉴에 있는지 알 수 있도록 선택된 메뉴를 비선택 메뉴와 다른 색상 또는 강조 바로 구분한다. 실제 선택 상태와 표시가 일치해야 한다.

사용자가 제공한 참고 이미지의 하단 바 구조와 선택 상태 표현을 참고한다. 이미지 속 메뉴명(메인·약속·알림·프로필)과 색상은 세단지의 확정 메뉴·색상으로 취급하지 않는다. 세부 색상, 강조 바 형태 및 위치는 화면 설계에서 정한다.

하단 메뉴는 지도·저장·제보·내 정보의 4개 탭으로 확정한다. 지도는 첫 진입의 주변 식당 탐색, 저장은 개인 저장 목록, 제보는 신규 식당 등록 제보, 내 정보는 계정·설정 기능의 진입점이다. 기존 식당 제보는 식당 상세 영역에서 시작한다. 저장 목록 이용에는 로그인이 필요하며, 제보 양식 작성은 비로그인 상태에서도 가능하고 최종 제출 시 로그인을 요구한다. 내 제보 상태 조회는 내 정보에서 접근하도록 하되 구현 후순위 원칙을 유지한다.

### 탭 이동과 앱 종료 시 상태 — 확정

| ID | 구분 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| NAV-01 | 확정 | 앱 실행 중 탭을 이동해도 지도 상태를 유지한다 | 지도 탭으로 돌아오면 이전 지도 위치·확대 수준·조회된 핀을 유지한다 |
| NAV-02 | 확정 | 앱 실행 중 탭을 이동해도 저장 목록의 스크롤 위치를 유지한다 | 저장 탭으로 돌아오면 이전 스크롤 위치에서 이어서 볼 수 있다 |
| NAV-03 | 확정 | 앱 실행 중 탭을 이동해도 제출 전 제보 입력 내용을 유지한다 | 제보 탭으로 돌아와 작성을 이어갈 수 있다. 접수 성공 후 양식 초기화 원칙은 유지한다 |
| NAV-04 | 확정 | 다른 탭으로 이동하면 영상 재생을 중지한다 | 탭 이동 후 영상과 음성이 계속 재생되지 않는다 |
| NAV-05 | 확정 | 앱 종료 후 재실행 시 이전 화면 상태를 복원하지 않는다 | 지도 위치·확대 수준·조회 결과, 목록 스크롤, 제출 전 제보 입력 내용 등 임시 화면 상태를 복원하지 않고 지도 탭의 첫 진입 흐름으로 시작한다 |

앱 종료 후 화면 상태를 복원하지 않는 것은 계정에 저장한 식당이나 접수 완료된 제보를 삭제한다는 뜻이 아니다. 계정 데이터와 AUTH-04에 따른 로그인 상태는 유지한다. 앱이 종료되지 않은 단순 백그라운드 전환을 앱 종료로 취급하지 않는다.

### 4.1 지도

핵심 기능은 **사용자 현 위치를 기준으로 주변에 등록·승인된 식당을 지도에 핀으로 표시하는 것**이다. 사용자는 셰프 선택 없이 주변 식당을 발견하고, 핀을 터치하여 상세 정보와 출처를 확인한다.

셰프를 선택하여 해당 셰프와 연결된 식당만 표시하는 필터는 사용자 편의를 위한 부가 기능으로 첫 출시부터 제공한다. 기본 탐색의 선행 조건으로 두지 않으며 기본값은 전체 셰프다. 한 번에 셰프 한 명을 선택할 수 있고 ‘전체’를 선택하면 필터를 해제한다. 선택한 셰프와 승인된 관계가 있는 식당만 지도 핀·지역별 클러스터 개수·식당 리스트에 동일하게 반영한다. 필터가 적용되어도 클러스터는 관계 수가 아닌 중복 없는 식당 수를 표시한다.

| ID | 구분 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| EXP-01 | 확정 | 모든 사용자는 로그인하지 않고 맛집을 탐색할 수 있다 | 앱의 공개 탐색 기능에 로그인 선행 조건이 없다 |
| EXP-02 | 확정 | 사용자 현 위치를 기준으로 주변에 등록·승인된 식당을 지도에 핀으로 표시한다 | 셰프를 선택하지 않아도 주변 식당을 탐색할 수 있다. 실제 확인된 장소의 좌표를 사용하며 다른 지점의 정보를 섞지 않는다 |
| EXP-03 | 확정 | 식당과 연결된 셰프, 출처 영상, 확인된 언급 유형을 확인할 수 있다 | 같은 식당을 소개한 서로 다른 셰프·영상의 근거를 구분한다 |
| EXP-04 | 확정 | 원본 영상과 확인된 언급 시점으로 이동할 수 있다 | 시점이 있으면 해당 시점을 포함한 공식 링크 또는 허용된 재생 방식으로 연결한다. 시점이 없으면 임의 값을 만들지 않는다 |
| EXP-05 | 확정 | 승인된 관계만 사용자에게 공개한다 | 미검증 후보·제보·내부 검토 메모는 탐색 결과에 포함하지 않는다 |
| EXP-06 | 확정 | 첫 진입 시 현 위치 주변의 등록·승인된 식당을 자동 조회한다 | 현 위치를 확보하면 별도 검색 버튼 조작 없이 주변 식당 핀을 표시한다 |
| EXP-07 | 확정 | 상세 탐색에서는 ‘이 지역에서 검색’ 버튼으로 식당 조회 결과를 갱신한다 | 상세 탐색 중 지도 이동만으로 식당 결과를 자동 갱신하지 않는다. 버튼을 누르면 이동한 지역의 등록·승인된 식당을 조회하여 핀을 갱신한다. 광역 클러스터 모드 전환은 EXP-11을 따른다 |
| EXP-08 | 확정 | 상세 탐색의 식당 조회 범위는 고정 반경이 아닌 현재 지도에 보이는 영역으로 정한다 | 첫 자동 조회는 초기 지도 영역, ‘이 지역에서 검색’은 버튼을 누른 시점의 지도 영역 안에 있는 등록·승인된 식당을 조회한다. 광역 모드의 전체 DB 집계와 구분한다 |
| EXP-09 | 확정 | 첫 진입은 현 위치를 중심으로 약 1~2km 주변을 살펴볼 수 있는 동네 수준의 확대 상태로 시작한다 | 1~2km는 초기 표시 규모의 기준이며 고정 검색 반경이 아니다. 정확한 SDK 확대 값은 화면 크기를 고려한 상세 설계에서 정한다 |
| EXP-10 | 확정 | 조회 결과가 없으면 빈 결과를 안내하고 사용자가 다른 지역을 탐색하도록 한다 | 지도 축소 또는 다른 지역 검색을 안내하며 검색 범위를 자동으로 넓히지 않는다. API·네트워크 실패를 빈 결과로 안내하지 않는다 |

빈 결과 안내 문구 초안: “이 지역에 등록된 식당이 아직 없어요. 지도를 축소하거나 다른 지역에서 검색해 보세요.” 정확한 문구와 배치는 상세 설계에서 정한다.

‘전체 지역으로 보기’를 누르면 선택한 셰프와 승인된 관계가 있는 전체 지역의 공개 식당이 모두 들어오도록 지도 범위를 맞춘다. 셰프 필터는 유지하며 결과 축척에 따라 기존 원칙대로 개별 핀 또는 지역별 클러스터를 표시한다. 식당이 한 곳뿐인 경우의 확대 수준과 지도 가장자리 여백 등 세부 값은 상세 설계에서 정한다.

광역 모드는 전체 식당을 기기에 내려받아야 한다는 뜻이 아니다. 지역별 개수와 표시 위치를 집계해 제공하는 구현을 검토한다. 기존의 지도 영역 조회 및 ‘이 지역에서 검색’ 방식은 상세 탐색에 적용한다.

클러스터 터치는 사용자가 명시적으로 요청하는 지역 확대·목록 조회다. 상세 탐색의 단순 지도 이동에 대한 ‘이 지역에서 검색’ 원칙과 구분한다. 식당 리스트는 개별 식당 핀을 터치하여 여는 식당 상세 영역과 구분한다.

시·도별 → 시·군·구별 → 상세 식당 핀으로 이어지는 표시 단계는 확정한다. 각 단계의 정확한 전환 축척, 행정구역별 집계의 세부 기준, 클러스터 터치 시 확대 수준, 동 정보가 없는 지역의 주소 요약 방식과 셰프 요약의 대표 이름 선정 기준, 거리 계산·표시 방식과 정렬 동률 처리, 다시 확대하여 상세 탐색으로 돌아올 때의 핀 조회 동작, 집계 갱신 주기와 상세 탐색 중 핀 묶음 기준은 아직 미정이다.

위치를 확보하지 못해도 지도 탐색을 계속할 수 있어야 한다.

안내의 정확한 문구·배치, 위치 조회 제한 시간, 서울 시청 기본 지역의 확대 수준은 구현 전 상세 설계에서 정한다. 현 위치 기반 첫 진입의 확대 규모는 EXP-09를 따른다. LOC-04의 ‘내 위치’ 동작은 지도 이동 후 수동 검색 원칙과 별도로 사용자가 명시적으로 요청하는 이동·조회다.

### 4.1.1 식당 상세 영역과 영상 재생 — 확정

식당 상세는 별도 화면으로 이동하지 않고 지도 위에서 슬라이드 업하는 상세 영역으로 제공한다. 상세 영역의 하단에 출처 영상 재생 영역을 둔다.

| ID | 구분 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| DETAIL-01 | 확정 | 지도에서 식당을 터치하면 상세 영역이 슬라이드 업한다 | 별도 상세 화면으로 이동하지 않고 지도 위에 선택한 식당의 상세 영역이 나타난다 |
| DETAIL-02 | 확정 | 상세 영역 하단에 출처 영상 영역을 제공한다 | 앱 내부의 YouTube 공식 임베드 플레이어로 영상을 재생할 수 있다 |
| DETAIL-03 | 확정 | 사용자가 재생 버튼을 누르기 전에는 영상을 재생하지 않는다 | 상세 영역 진입이나 영상 영역 표시만으로 자동 재생하지 않는다 |
| DETAIL-04 | 확정 | 재생 버튼을 누르면 확인된 타임스탬프를 사용해 해당 소개 시점부터 재생한다 | 선택한 출처 영상과 해당 관계의 확인된 타임스탬프를 사용한다. 상세 영역 안에서 재생한다 |
| DETAIL-05 | 확정 | 확인된 타임스탬프가 없으면 재생 버튼을 눌렀을 때 영상 처음부터 재생한다 | 타임스탬프 없이도 수동 재생이 가능하다. 재생 시작점을 처음으로 정하는 것은 확인된 언급 시점이 0초라는 뜻이 아니며, 미확인 시점은 값 없음으로 유지한다 |
| DETAIL-06 | 확정 | 상세 영역을 닫거나 식당 리스트로 돌아가면 영상 재생을 중지한다 | 상세를 닫거나 리스트로 전환한 뒤에는 해당 영상의 화면 재생과 음성이 계속되지 않는다 |
| DETAIL-07 | 확정 | 상세 영역에 식당 이름과 전체 주소, 확인 가능한 현 위치와의 거리, 저장 버튼을 표시한다 | 리스트의 시·군·구·동 요약 주소와 달리 상세에서는 전체 주소를 확인할 수 있다. 현 위치를 모르면 거리를 표시하지 않으며 저장은 기존 로그인 조건을 따른다 |
| DETAIL-08 | 확정 | ‘카카오맵에서 보기’를 제공한다 | 해당 식당의 카카오맵 장소로 외부 연결하여 길찾기나 추가 정보를 확인할 수 있게 한다. 다른 지점으로 연결하지 않는다 |
| DETAIL-09 | 확정 | 소개한 셰프와 관계 유형을 표시한다 | 승인된 관계를 기준으로 단골·추천·방문·언급을 구분하여 표시하고 관계의 의미를 임의로 강화하지 않는다 |
| DETAIL-10 | 확정 | 하단 출처 영상 리스트의 각 항목에 셰프 이름·영상 제목·채널명·확인된 타임스탬프·재생 버튼을 표시한다 | 각 출처에 연결된 셰프와 시점을 구분한다. 미확인 시점을 확인된 0초처럼 표시하지 않으며 재생 동작은 DETAIL-03~05를 따른다 |
| DETAIL-11 | 확정 | 영상은 한 번에 하나만 재생한다 | 다른 영상의 재생 버튼을 누르면 기존 영상의 영상·음성 재생을 중지하고 선택한 영상을 재생한다. 선택한 영상의 시작 시점은 DETAIL-04~05를 따른다 |
| DETAIL-12 | 확정 | 앱 내부에서 영상을 재생할 수 없으면 안내와 ‘YouTube에서 보기’ 버튼을 제공한다 | 외부 앱이나 브라우저로 자동 이동하지 않고 사용자가 버튼을 눌렀을 때 해당 영상의 공식 YouTube 링크로 연결한다. 확인된 타임스탬프가 있으면 링크에 포함한다. 외부 연결이 삭제·비공개 등 원본 영상의 접근 제한을 해소한다고 안내하지 않는다 |
| DETAIL-13 | 확정 | 출처 영상 리스트는 영상 게시일 최신순으로 정렬한다 | 서비스 등록일이 아닌 원본 영상의 게시일을 기준으로 최근 영상부터 표시한다 |

출처 영상이 여러 개라면 상세 영역 하단에 리스트로 나열한다. 사용자가 각 영상의 재생 버튼을 누르면 해당 영상에 연결된 확인된 타임스탬프부터 재생하고, 타임스탬프가 없으면 처음부터 재생한다. 리스트를 표시하는 것만으로 영상을 재생하지 않는다.

게시일이 같거나 누락된 영상의 세부 정렬 기준은 미정이다. 확인되지 않은 타임스탬프를 임의로 만들지 않는다. 지도 네이티브 SDK 사용과 영상 영역의 공식 임베드 사용은 별개다.

### 슬라이드 업 영역의 높이와 닫기 — 확정

식당 리스트와 상세 영역은 처음에 화면 절반 정도로 표시하고, 위로 끌면 화면 대부분까지 확장한다. 아래로 끌 때는 중간 높이로 축소하여 멈추는 기능 없이 닫기만 제공한다. 닫기 버튼도 제공한다. 닫기에 필요한 드래그 거리·속도와 정확한 높이는 상세 설계에서 정한다.

리스트에서 상세로 진입한 뒤 뒤로 가면 기존 리스트의 높이와 스크롤 위치를 복원한다. 상세에서 리스트로 돌아가는 동작과 영역 전체를 닫는 동작은 구분하며, 두 경우 모두 기존 합의대로 영상 재생을 중지한다.

첨부된 지도 앱 이미지 두 장은 높이 설정의 기준으로 사용한다. 첫 번째 이미지는 초기 표시 높이(화면 절반 정도), 두 번째 이미지는 위로 끌어 확장한 높이(화면 대부분, 상단에 지도가 조금 보이는 수준)를 참고한다. 기기별 화면 크기와 안전 영역을 고려하여 이 비율과 모습을 반영한다. 이미지의 사진·평점·카테고리·메뉴 구성을 제품 요구사항에 추가하는 것은 아니다.

### 4.3 맛집 제보

제보는 **식당 등록 요청의 접수**다. 제출만으로 식당이나 셰프–식당 관계가 공개되지 않는다. 미등록 식당의 정보를 사용자에게 받을 수 있어야 한다.

#### 입력 항목 — 확정

| ID | 항목 | 필수 여부 | 의미 |
| --- | --- | --- | --- |
| SUB-F01 | 셰프 이름 | 필수 | 사용자가 해당 식당을 소개했다고 알고 있는 셰프 이름 |
| SUB-F02 | 식당 이름 | 필수 | 신규 등록 제보에서는 사용자가 입력한다. 기존 식당 제보에서는 선택한 등록 식당 정보를 자동으로 포함하므로 사용자가 다시 입력하지 않는다 |
| SUB-F03 | 영상 링크 | 선택 | 관리자가 출처를 확인할 수 있는 영상 링크 |
| SUB-F04 | 타임스탬프 | 선택 | 소개 장면으로 추정하거나 확인한 영상 시점 |
| SUB-F05 | 소개 내용 | 선택 | 어떤 내용으로 소개했는지 등 사용자가 알려주려는 정보 |

#### 제보 동작

| ID | 구분 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| SUB-01 | 확정 | 셰프 이름과 식당 이름만 입력해도 접수 가능한 제보로 취급한다 | 영상 링크·시점·소개 내용이 없어도 자료 누락만을 이유로 제출을 차단하지 않는다. 최종 제출할 때만 로그인을 요구한다. |
| SUB-02 | 확정 | 영상 링크와 시점을 제공하면 검토가 빨라진다고 명시한다 | 제보 입력 과정에서 두 정보의 제공이 검토에 도움이 됨을 알 수 있다 |
| SUB-03 | 지침 | 사용자가 입력한 셰프 이름과 식당 이름을 검증된 식별자로 간주하지 않는다 | 동명이인과 동일 상호의 다른 지점은 관리자가 확인한다 |
| SUB-04 | 지침 | 제보의 원래 내용과 관리자의 확인 결과를 구분한다 | 검토 과정에서 확보한 출처·주소·관계 유형을 제보자의 원래 주장처럼 바꾸지 않는다 |
| SUB-05 | 지침 | 제보만으로 공개 식당이나 승인 관계를 자동 생성하지 않는다 | 접수는 성공해도 사용자 탐색에 바로 나타나지 않는다 |
| SUB-06 | 지침 | 영상 링크가 없는 제보는 출처 확인이 필요한 자료로 남긴다 | 관리자가 공개 조건을 충족할 근거 영상을 확보하기 전에는 관계를 승인하지 않는다 |
| SUB-07 | 확정 | 제보 작성 중 로그인 과정에서 입력 내용을 유지한다 | 로그인 성공·취소·실패 모두 기존 입력 내용을 잃지 않는다 |
| SUB-08 | 확정 | 로그인 성공 후 제보 양식으로 돌아와 사용자가 최종 제출한다 | 로그인 성공만으로 제보를 자동 제출하지 않는다 |
| SUB-09 | 확정 | 제출 성공 후 접수 완료 안내와 함께 양식을 초기화한다 | 서버의 접수 성공을 확인한 뒤 안내하고 초기화한다. 제출 실패 시에는 성공으로 표시하거나 입력 내용을 초기화하지 않는다 |

입력 기준은 다음과 같이 확정한다.

- 셰프 이름과 신규 등록 제보의 식당 이름은 필수이며 각각 최대 100자다. 공백만 입력한 경우 미입력으로 처리한다.
- 영상 링크는 선택이며 첫 출시에는 YouTube 영상 링크만 허용한다.
- 타임스탬프는 선택이며 `분:초` 또는 `시:분:초` 형식으로 입력한다.
- 소개 내용은 선택이며 최대 2,000자다.
- 영상 링크 없이 타임스탬프만 입력해도 접수한다. 타임스탬프를 입력했다는 이유로 영상 링크를 필수로 바꾸지 않는다.

선택 항목도 입력한 경우 해당 형식과 길이를 검증한다. 허용할 YouTube URL의 세부 형태, 시간 구성값의 유효 범위와 정확한 오류 문구는 상세 설계에서 정한다. 사용자 입력 시점은 관리자 확인 전까지 검증된 시점으로 취급하지 않는다.

입력 안내 문구 초안:

> 아직 지도에 없는 맛집을 알려주세요. 어떤 셰프가 어느 식당을 소개했는지 제보해 주세요. 영상 링크와 해당 장면의 타임스탬프를 함께 남겨주시면 등록 검토가 훨씬 빨라집니다. 제보는 관리자 확인 후 지도에 반영됩니다.
> 

‘영상 링크+타임스탬프 제공 시 검토가 빨라짐’이라는 안내 의도는 확정이며, 위의 정확한 문구와 배치는 제안이다. 제공 여부만으로 공개를 보장하거나 처리 기한을 약속하지 않는다.

#### 신규 등록 제보와 기존 식당 제보 — 확정

신규 등록 제보와 이미 등록된 식당에 대한 제보는 별도 흐름으로 제공한다. 신규 등록 제보는 기존 입력 항목을 따르고, 기존 식당 제보는 선택한 식당을 대상으로 시작한다.

| ID | 구분 | 요구사항 | 수용 기준 |

## 5. 관리자 웹 요구사항

관리자 웹은 맛집 등록을 위한 전용 도구다. 기존에 구현된 화면 구성은 사용자 승인된 구성안으로 취급하지 않는다.

### 관리자 웹 메뉴 — 확정

관리자 업무 메뉴는 **제보 관리·식당 관리 두 개**로 구성한다.

- 제보 관리: 신규 등록 제보와 기존 식당 제보를 확인하고 검토·처리한다.
- 식당 관리: Kakao Local API 장소 검색·등록, 기존 식당 조회, 셰프·영상 관계 추가, 임시 저장·승인·정정·공개 중단·복구를 처리한다.

셰프 검색·신규 입력과 출처 영상 확인은 식당 관리 흐름 안에서 제공한다. 셰프 관리·관계 관리·출처 확인 필요 목록을 각각 별도 업무 메뉴로 만들지 않는다. 재확인이 필요한 출처는 식당 관리 내 필터나 표시로 구분한다. 세부 화면 배치와 입력 구성은 별도 검토한다.

### 관리자 제보 목록 — 확정

목록에는 신규/기존 식당 제보 구분, 식당명, 셰프명, 접수일, 처리 상태를 표시한다. 상태별 필터를 제공하며 기본 목록에는 접수·검토 중인 제보를 표시한다. 정렬은 접수일이 오래된 순으로 한다.

### 관리자 식당 목록 — 확정

목록에는 식당명·주소·연결 셰프·공개 가능한 관계 수를 표시한다. 식당명·주소·셰프명으로 검색할 수 있고, 공개 중·공개 관계 없음·출처 재확인 필요 필터를 제공한다. 정렬은 최근 등록순으로 한다.

### 장소 선택 불가 시 처리 — 확정

Kakao Local API의 장소 검색이 정상 완료됐으나 결과가 없거나, 여러 결과 중 실제 지점을 확정할 수 없으면 임의로 장소를 선택하거나 주소·좌표를 직접 입력해 등록하지 않는다. 재검색 단계로 이어가지 않고 시작 경로에 따라 아래와 같이 처리한다.

- 직접 등록: 식당을 선택할 수 없으므로 등록을 중단한다. 식당·관계·별도 보류 자료를 생성하지 않는다.
- 사용자 제보 검토: 원본 제보에 장소 검색 결과 없음 또는 실제 지점 확정 불가 사유를 기록하고 반영 보류로 처리한다. 근거 확보 후 기존 검토 재개와 이력 보존 규칙을 적용한다.

API 인증·할당량·네트워크·응답 오류는 검색 결과 없음으로 취급하지 않으며, 오류만으로 제보를 자동 보류하지 않는다.

### 관리자 작성 중 이탈 — 확정

관리자가 작성 중 저장하지 않은 변경 사항이 있는 상태로 이탈하려 하면 ‘저장하지 않고 나가기 / 계속 작성’ 확인창을 표시한다. 저장하지 않고 나가기를 선택하면 미저장 변경을 버리고 이동하며, 계속 작성을 선택하면 현재 입력을 유지한다. 자동 저장은 수행하지 않는다.

이는 관리자 웹 내부에서 제어할 수 있는 화면·메뉴 이동과 양식 닫기에 적용한다. 브라우저 탭 닫기·새로고침에는 브라우저가 허용하는 기본 이탈 경고를 사용하며, 사용자 지정 문구나 강제 종료 시 경고 표시를 보장하지 않는다. 마지막으로 명시적으로 저장한 임시 자료와 승인 자료는 미저장 변경을 버려도 유지한다.

### 검증 메모 — 확정

검증 메모는 관리자가 승인 판단의 근거를 남기는 선택 항목이다. 메모 미입력만으로 승인을 차단하지 않는다. 확인된 타임스탬프도 선택 항목이며 미확인은 값 없음으로 유지한다. 이 결정은 정정·복구·보류 시 별도로 기록하기로 한 사유를 선택 항목으로 바꾸지 않는다.

### 출처 영상 등록 — 확정

관리자가 YouTube URL을 입력하면 공식 YouTube Data API로 영상 제목·채널·게시일을 조회한다. 추출한 videoId가 이미 등록되어 있으면 기존 영상을 재사용하여 관계에 연결하고 중복 영상을 만들지 않는다. API 조회 실패 시 오류 안내와 재시도를 제공한다. 조회된 제목·채널만으로 셰프의 추천이나 관계 유형을 자동 판단하지 않는다.

### 관리자 식당 등록 화면 구성 — 확정

[관리자 식당 등록 시안](design/admin-restaurant-registration.png)의 2단계 구성을 채택하고 구현 시 참고한다.

1. 장소 검색·선택: 식당명으로 Kakao Local API를 검색하고 후보의 이름·주소·Kakao Place ID를 확인한다. 카카오맵 확인과 실제 지점 선택을 제공한다. 결과 없음·지점 확정 불가 시 기존 중단·제보 보류 규칙을 적용한다.
2. 관계 입력·승인: 선택한 식당을 표시하고 셰프 검색·신규 입력, YouTube URL 및 메타데이터 조회, 관계 유형, 선택 타임스탬프·검증 메모를 입력한다. 취소·임시 저장·승인 및 공개 동작을 제공한다. 임시 저장 최소 조건과 승인 조건을 구분한다.

기존 장소·셰프·영상 재사용, 중복 관계 처리, 미저장 이탈 확인 등 확정 규칙을 공통 적용한다. 시안의 영상·셰프 관계와 날짜는 예시이며 실제 검증 자료가 아니다. 세부 스타일·문구는 상세 설계에서 정한다.

### 관리자 식당 상세 구성 — 확정

사용자가 검토한 관리자 식당 상세 시안의 구성을 채택한다. 시안은 [관리자 식당 상세 화면 참고 이미지](design/admin-restaurant-detail.png)로 프로젝트에 보관하며, 해당 화면을 구현할 때 이 자료와 아래 확정 요구사항을 참고한다.

- 상단에 식당명·전체 주소·Kakao Place ID·카카오맵 링크를 표시한다.
- 하단에 셰프·영상별 관계 목록과 공개 상태를 표시하고 관계 추가 버튼을 제공한다.
- 각 관계에 셰프·관계 유형·출처 영상·채널·확인된 타임스탬프를 표시한다. 시점이 없으면 미확인으로 구분한다.
- 관계 상태에 맞는 승인·정정·공개 중단·복구 작업과 영상 확인을 제공한다. 기존 재승인·사유 기록·권한 규칙을 적용한다.
- 변경 이력은 해당 관계 아래에서 펼쳐 확인할 수 있도록 하고 별도 관리 메뉴로 분리하지 않는다.

시안의 셰프·영상·처리 일시는 구성 예시이며 실제 검증된 관계나 운영 이력으로 취급하지 않는다. 세부 색상·간격·이미지 자산과 최종 문구는 구현 전 상세 설계에서 정한다.

### 관리자와 사용자 권한 — 확정

초기 운영은 관리자 한 명이 담당한다. 작성자와 승인자를 분리하지 않고 관리자가 등록·검토·승인·정정·공개 중단·복구를 모두 수행할 수 있다. 본인이 작성한 자료도 직접 승인할 수 있으며 각 처리의 이력 기록 원칙은 유지한다.

일반 사용자는 공개 데이터의 등록·변경 과정에서 제보만 할 수 있다. 식당·셰프·영상·관계를 직접 등록하거나 승인·정정·공개 중단·복구할 권한은 없다. 이는 기존에 확정한 공개 탐색·개인 저장·계정 기능을 제한한다는 뜻이 아니다.

공개 가능한 관계가 없어 탐색에서 제외된 식당은 SAVE-10에 따라 저장 기록을 유지하면서 저장 목록에서 일시 제외하고, 다시 공개되면 표시한다. ‘현재 공개되지 않은 식당’ 등의 운영 상태 안내는 제공하지 않는다.

공개 중단한 관계를 복구하려면 관리자가 근거를 다시 확인하고 복구 사유를 기록한 뒤 재승인해야 한다. 수정 내용을 저장하는 것만으로 자동 복구하지 않는다. 복구 처리자·시각과 승인 이력을 기록한다. 복구된 관계가 공개 조건을 충족하면 해당 관계를 다시 공개하고, 그 결과 식당이 다시 공개 가능해지면 지도·검색·클러스터와 기존 저장 목록 표시에도 반영한다.

### 출처 영상의 삭제·비공개 처리 — 확정

이미 검증·승인된 관계의 출처 YouTube 영상이 삭제되거나 비공개되어도 해당 관계와 식당을 자동으로 숨기지 않는다. 사용자에게는 해당 영상의 재생 불가를 안내하고, 관리자에게는 출처 확인이 필요한 대상으로 남긴다. 관리자 확인 중이라는 내부 상태는 사용자에게 표시하지 않는다.

기존 영상 식별자와 관계의 검증 이력을 보존한다. 이 정책은 출처 영상 없이 새로운 관계를 승인할 수 있다는 뜻이 아니다. 확인 결과 관계 자체에 문제가 있으면 기존 정정·공개 중단 절차로 처리한다. 영상 접근 상태의 확인 시점·주기와 관리자 확인 목록의 구성은 상세 설계에서 정한다.

중복 등록 과정에서 기존 관계의 타임스탬프·유형 등을 수정하도록 유도하지 않는다. 잘못된 자료는 별도 관리자 정정 기능으로 처리하며 공개 정보의 수정안은 재승인 후 반영한다. 정정 가능한 필드, 승인 취소와 공개 중단의 상세 운영 정책은 별도로 정한다.

관리자 직접 입력, 사용자 제보, 자동 추출 후보는 모두 검토의 입력이 될 수 있다. 자동 추출은 보조 수단이며, 설명란에 식당이나 주소가 없어도 관리자가 확보한 적절한 근거로 등록을 검토할 수 있어야 한다.

제보 반영 결과를 제보자에게 통지하는 상세 방법과 승인 취소 등 추가 운영 절차는 아직 정하지 않았다. 제보 처리 푸시 알림은 기존 합의대로 첫 출시에서 제외한다.

## 7. 확정된 이용 흐름과 제안 흐름

### 7.1 로그인 없는 탐색 — 확정

첫 진입 → 현 위치 확보 → 주변의 등록·승인된 식당 자동 조회 및 핀 표시 → 지도 탐색 → 식당 터치 → 지도 위로 식당 상세 영역 슬라이드 업 → 셰프·출처 정보 확인 → 원하는 경우 상세 영역 하단의 영상 재생 버튼 터치 → 확인된 타임스탬프부터 앱 내부 재생(타임스탬프가 없으면 영상 처음부터 재생). 이후 지도를 다른 지역으로 이동하면 ‘이 지역에서 검색’ 버튼을 눌렀을 때 해당 지역 식당을 조회하여 핀을 갱신한다. 이 흐름에서 로그인을 필수로 요구하지 않으며, 재생 버튼을 누르기 전에는 영상을 재생하지 않는다.

### 7.2 개인 저장 — 확정

식당 저장 시도 → 비로그인이라면 로그인 안내 → 로그인 성공 후 해당 식당 저장. 로그인 취소·실패 시 저장 완료로 표시하지 않는다.

### 7.3 사용자 제보 — 확정 부분과 미정 부분

셰프 이름·식당 이름 입력 → 원하는 경우 영상 링크·타임스탬프·소개 내용 추가 → 최종 제출 시 로그인 확인 → 제보 접수 → 관리자 검증 → 공개 조건 충족 시 반영.

최종 제출 시 로그인은 필수다. 비로그인 사용자가 제출을 시도하면 입력 내용을 유지한 채 로그인으로 연결하고, 로그인 성공 후 양식으로 돌아와 사용자가 최종 제출한다. 로그인 취소·실패 시에도 입력 내용은 유지한다. 접수 성공 후 완료 안내와 함께 양식을 초기화하며 제출 실패 시 입력 내용을 유지한다. 내 제보 상태 조회는 확정된 구성으로 후순위 구현한다. 공개 조건을 충족하지 못한 제보는 즉시 공개하지 않는다.

### 7.4 관리자 제보 처리 — 확정 부분과 미정 부분

제보 상세 확인 → ‘등록 검토’ 선택 → 제보 내용을 미리 채운 식당 관리 등록 양식 → 중복·실제 지점 및 출처 확인 → 관계 유형 검증 → 임시 저장 또는 검토·승인 후 공개 반영. 기존 식당 제보는 대상 식당을 자동 연결한다. 제보 원문은 보존하고 관리자 확인 결과와 별도로 관리한다.

제보 상태 변경 시점은 다음과 같이 확정한다.

| 상태 | 변경 시점 |
| --- | --- |
| 접수 | 사용자 제보 제출이 성공했을 때 |
| 검토 중 | 관리자가 ‘등록 검토’를 시작했을 때 |
| 반영 완료 | 관계 승인·공개와 해당 제보의 반영 결과 연결이 완료됐을 때 |
| 반영 보류 | 근거 부족·중복 등으로 진행하지 않기로 처리했을 때. 사유를 기록한다 |

반영 보류한 제보는 관리자가 ‘검토 재개’를 선택하면 검토 중 상태로 되돌린다. 기존 보류 사유와 처리 이력을 보존하고 재개 처리자·시각을 기록한다. 검토 재개만으로 관계를 승인하거나 사용자 앱에 공개하지 않으며, 반영 완료는 기존 승인·공개 조건을 따른다.

중복으로 보이는 제보도 사용자 입력만으로 자동 차단하지 않고 접수한다. 관리자가 다른 지점이나 새로운 근거인지 확인하여 판단한다. 실제 중복이면 반영 보류로 처리하고 중복 사유를 기록하며, 중복 대상인 기존 자료와 연결한다. 기존 자료는 관리자 검토를 위한 연결이며 사용자에게 내부 자료를 노출하지 않는다.

관리자의 제보 처리와 상태 기록부터 구현하며 사용자 내 제보 조회 화면은 후순위로 유지한다. 사용자에게도 동일한 4단계 상태를 표시하되 관리자 내부 메모와 공개용 보류 사유는 구분한다. DB 상태의 세부 설계는 별도로 정하며 Mention의 검증 상태와 제보 처리 상태를 동일시하지 않는다. 첫 출시에는 추가 정보 요청·제보자 답변 기능을 포함하지 않는다.

| QLT-02 | 지침 | 비밀키·인증 헤더·비밀번호를 소스·로그·공개 응답에 노출하지 않는다 | 코드·설정·응답·로그 검토 |
| QLT-03 | 지침 | 외부 API 실패와 할당량·조회 불가 상황을 처리한다 | 실패를 정상 완료나 데이터 부재로 오인하지 않는 테스트 |
| QLT-04 | 지침 | 공식 YouTube API와 허용된 영상 연결 방식을 사용한다 | 권한 없는 자막 다운로드·접근 제한 우회가 없다 |
| QLT-05 | 지침 | 제보·후보·장소 매칭 결과가 자동 공개로 이어지지 않는다 | 접수·검색 전후 공개 자료가 임의로 늘지 않는 테스트 |
| QLT-06 | 지침 | DB 구조 변경은 기존 자료와 근거를 보존하도록 계획한다 | ERD·후속 Flyway·데이터 이관 테스트 검토 |

iOS·Android에서의 기능 범위 차이, OS 최소 버전, 접근성 세부 기준, 응답 시간·처리량·제보 검토 기한 등은 임의의 수치로 확정하지 않는다.

## 10. 구현·화면 설계 진행 원칙

1. 본 명세서의 확정 사항과 미정 사항을 사용자와 검토한다.
2. 첫 출시 기능과 우선순위를 합의한다.
3. 기능에 필요한 화면 목록과 이용 흐름을 제안한다.
4. 사용자가 화면 구성안을 확인한 뒤 상세 설계와 구현을 진행한다.
5. 앱 기술 등 기존 지침에 없는 선택은 이유와 영향을 설명한 뒤 결정한다.

기존 화면의 재배치, 모바일 전환, 제보 화면 추가를 이 문서 작성과 동시에 진행하지 않는다. 기존 PoC와 웹 기능의 검증 이력을 iOS·Android 앱이나 사용자 저장·제보 기능의 완료 근거로 사용하지 않는다.

## 11. 현재 요구를 점검할 대표 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 비로그인 사용자가 맛집과 근거를 탐색 | 로그인 없이 확인 가능 |
| 비로그인 사용자가 특정 식당 저장 시도 | 로그인 안내 후 성공하면 같은 식당을 저장 |
| 사용자 A가 사용자 B의 저장 목록에 접근 시도 | 조회·변경 차단 |
| 셰프 이름·식당 이름만 제공 | 선택 정보가 없다는 이유로 제보를 막지 않음. 최종 제출 시 로그인 필요 |
| 영상과 시점이 포함된 제보 | 검토자가 해당 출처와 시점으로 접근할 수 있는 정보를 보관 |
| 영상 없는 제보 | 미검증 정보로 접수하고 관리자가 근거 확보 후 공개 여부 판단 |
| 상호는 같지만 다른 지점 | 장소를 확정하지 않고 지점 확인 필요 상태로 검토 |
| 장소가 일치하지만 추천 사실은 미확인 | 추천·단골 관계로 자동 공개하지 않음 |
| 식당 후보는 있으나 승인된 관계가 없음 | 사용자 앱에 승인된 맛집처럼 노출하지 않음 |

이 표는 요구사항의 수용 기준 초안이다. 해당 기능이 이미 구현되거나 테스트됐다는 뜻은 아니다.
